# 传输层（Transport Layer）

## 3.1 概述

传输协议向上层提供的是**进程与进程**之间的**逻辑上的通信**。--->也就是所谓的port之间的通信.

字节流,没有消息边界.

网络层是主机之间的逻辑通信。

那么传输时就是源端复用（大家都可以使用一个TCP实体），目标端解复用（其实就是相当于聚合以及拆分的过程）。

传输层依赖于网络层，所以无法有**带宽**以及**延时**的保证。

> 什么是连接?
>
> 一组消息集合的**确认**--->**socket + seqNumber + winSize**

### 唯一确定一个TCP连接

四元组:

- 源地址
- 源端口
- 目的地址
- 目的端口

> 如果有一个server在一个port上面监听,最多可以建立多少个TCP连接.
>
> ​	所有客户端的IP * 所有可能的端口--->2^32 * 2^16 = **2^48**

但是肯定有限制:

1.文件描述符fd的数量限制.

```sh

```

2.内存限制.

#### *Sliding Window（滑动窗口协议）

sw：发送窗口 rw：接收窗口（我们设置窗口长度不能大于某个值（就是缓冲区的值的大小））

​	我认为用一个双端队列来理解是很形象的：队列长度不能大于某个设定的值，**队列中存放的都是已经发送但是没有得到ack的packet**，每当接收到一个ack，就从队列的头部pop出来，每当发送一个，就把这个packet push进入队列的尾部。

##### **sending window**

​	发送窗口的大小一定由接收方来确定,我们要保证发送的速率在接收方的可处理范围之内才可以.

​	二者的大小可能是约等于的.

![image-20250412175159365](../mio/static/img/image-20250412175159365.png)

**receiving window**

只有落在rw之内的序号的分组可以被接收，那么当rw = 1,只能顺序的接收，rw > 1的时候可以乱序的接收分组。

只有当rw中的第一个分组接收到时，它向sw发送ack，并且解封装数据向上交给用户，此时才可以向后进行滑动。

##### 1.sw = 1 rw = 1 --- 》 stop and wait 协议

##### 2.sw > 1 rw = 1 --- 》Go back to N 协议

为什么叫回退N步协议：

​	当sw的最低的分组再次收到ack（分组传的有问题）的时候，它要把之后都已经放出去的分组再传一遍，因为此时rw一定无法接收到最低位的分组之后的那些分组，因为rw的窗口大小只有一个，全部重传，所以叫回退。

​	**sw端只设置一个定时器，超时直接全部重传未确认的分组。**

​	顺序接收分组 这叫**累计确认**：这个ack之前的所有分组都收到了。

> 累计确认就是,不管之前Server返回的ACK是否全都到了,Client只认最新返回的ACK序列号.

##### 3.sw > 1 rw > 1 ---》 selective repeate 协议

​	可以乱序接收 独立确认。

​	**每个分组都有一个定时器。每个都要单独确认。**

##### 对比：

sr：重传代价小，但是要缓冲区代价。

GBN：重传代价大，但是没有缓冲区代价。

补充：

​	在**传输**的时候，我们会用一个**Nbits**的数来作为一个序号，用以标识分组，就和开始的01一样，它最多有2的N次方个序号，这叫**序号空间大小**。

​	窗口大小是说，我最多可以发送多少个未经确认的分组。

​	那么如下：

**Go-Back-N 协议分析**

- 在 Go-Back-N 中，**接收方只接收有序分组**，如果某个分组丢了，后面到达的分组全部丢弃。
- 接收方只需要记录**一个期望的序号** `expected_seq_num`。

**为什么最大窗口可以是 `2ⁿ - 1`？**

因为只要 **发送窗口的大小 < 序号空间大小**，发送方和接收方就不会对分组产生歧义。

举例说明（假设 `n = 3`）：

- 序号空间为 `0~7`，总共 `2³ = 8` 个序号。
- 如果发送窗口大小为 `7 = 2³ - 1`，就永远不会出现发送窗口“包裹”一整圈，从而使新分组和旧分组的序号重复混淆。

------

**Selective Repeat 协议分析**

- 在 Selective Repeat 中，接收方会**缓存失序到达的分组**，而不是像 GBN 一样全扔。
- 接收方需要**维护一个接收窗口**，并对每个分组做单独确认。
- 问题来了：**接收方如何知道一个分组是当前窗口的，还是旧的重复包？**

为什么窗口大小最多只能是 `2ⁿ⁻¹`？

因为：

> 如果窗口大小大于等于 `2ⁿ⁻¹`，那么当发送窗口“包裹一圈”时，可能会出现**新的分组和旧的分组使用相同的序号**，从而导致接收方产生**混淆**。

**举个例子（n = 3）：**

- 序号空间为 `0~7`

- 如果窗口大小是 `4 = 2ⁿ⁻¹`，假设当前接收窗口是 `[0,1,2,3]`，一切正常

- 但如果窗口大小是 `5`（大于一半），接收方可能无法区分：

  - 当前窗口的 `0`

  - 和上一个窗口周期已经收到过的旧的 `0`（重传包）

    **为什么会出现上面这样的情况，假如rw都已经全部正确接收，向后滑动了，但是ack0却没有正确的送达，此时sw会卡住，超时重传ack0,此时rw中又出现了0的序号，这就造成了混淆，所以不能大于一半的序号空间。**

这样就造成 **歧义和错误接收**。

###### 序号 确认号

​	序号：传输的字节流中每个MSS第一个字节（**载荷部分的第一个字节在原来的字节流中的**）的偏移量，这个offset还会加上某个值（开始的时候会相互约定好），防止网络中一些旧的分组造成影响。

> 注意是**字节的偏移**而不是一个一个的MSS的偏移量,如下图中表示的一样。

![image-20250415154728027](../mio/static/img/image-20250415154728027.png)

​	确认号是对于对方法发送过来的数据的确认，比如S发送分组给R（此时为0-353），那么R返回的**ACK中是它想要的下一个分组的序号（354）**，并且证明了之前的分组都已经正确的接收了（**累积确认**）。

​	并且这样的确认有可能是“捎带”在数据中的。

###### 超时重传

​	要设置合适的超时时间，不能太长但是也不能太短，那就要设置合适的自适应时间（根据实际情况动态调整）。

> 那么理论上,这个时间略微大于RTT是最合适的.

​		**EstimatedRTT = (1 – α) * EstimatedRTT + α * SampleRTT**（a = 0.125）

​		当前估计时间=前一段的估计时间 + 当前采样的RTT时间（两者会取一个权重，类似于均值）

​		这叫 **指数加权移动平均** 前面的影响对于后面的影响以指数规律下降。



变化的问题？我们还要考虑偏差值的问题。

​	**DevRTT = (1 – β) * DevRTT + β * | SampleRTT – EstimatedRTT |**（ β = 0.125）

​	对于这样的偏差值用同样的手法来处理。（类似于标准差）



最终，我们设置这个值为

**TimeoutInterval = EstimatedRTT + 4 * DevRTT**

这有点像正态分布中的原则。

###### *怎么实现TCP的RDT（可靠数据传输）

> 我们以下讲的都是传输的过程（不是握手挥手的问题）。

只会设置一个定时器，只和最早的未被确认的segment相关联。

如果超时，也只会重发最老的那个segment。

以下是一个简化的TCP发送方的行为：

```c
/* Assume sender is not constrained by TCP flow or congestion control, that data from above is less
than MSS in size, and that data transfer is in one direction only. */
NextSeqNum=InitialSeqNumber
SendBase=InitialSeqNumber
    
loop (forever) {
	switch(event)
	event: data received from application above
	create TCP segment with sequence number NextSeqNum
        
if (timer currently not running)
	start timer
	pass segment to IP
	NextSeqNum=NextSeqNum+length(data)
	break;
    
	event: timer timeout
	retransmit not-yet-acknowledged segment with
	smallest sequence number
	start timer
	break;
    
	event: ACK received, with ACK field value of y
        
if (y > SendBase) {
	SendBase=y
if (there are currently any not-yet-acknowledged segments)
	start timer
}
	break;
} /* end of loop forever */
```

注意到这个过程中，当我们收到ACK号的时候会对于base的值进行更改。

如果base和next的值相同，表明没有已经发送但是未收到ack的分组，此时关掉定时器。

考察几种情况：

确认丢失的重传。

![image-20250417153058053](../mio/static/img/image-20250417153058053.png)

想要的字节序号是92 + 8 = 100,那么发送一个ack100。



只对于顺序最新的未收到的segment发送请求，所以这里92重传了之后，返回的ack还是120。

![image-20250417153422972](../mio/static/img/image-20250417153422972.png)

以下是我们什么时候返回一个ACK：

![image-20250417153915842](../mio/static/img/image-20250417153915842.png)

​	1.按顺序到达的segment，我先不动，设置一个500ms的定时器，再来一个之后我再返回ack，如果500ms之内没有来，那么就直接返回ack（相当于可以精简这个过程，但是最多就只能接收两个segment,提高了利用率）。

​	2.乱序到达的segment，不是我本次想要的segment，就发送 **冗余ACK** 这个冗余ack就是我期待的顺序字节序号，每次乱序到达一次，都发送这样一个冗余ack。

###### **快速重传**：

![image-20250417154916591](../mio/static/img/image-20250417154916591.png)

​	当连续三个冗余ack都到达的时候（返回的冗余一定等于base，那就给base做计数的操作），就要发送这个ack请求的segment（此时应该一共接受了4个ack，第一个是正常的ack,不管是否超时）。

但是还是有问题:我们重传几个包?

1.如果丢了100 和 120,但是server只会返回100,我们只重传100,之后还要server再发送三次120才会重传120.

2.但是如果直接重传100-141,又很浪费!

###### 选择性确认重传(Selective Acknowledgement)--->SACK

> 附加一个**SACK**字段,这会告诉发送方,哪些数据是已经收到的.

还有**Duplicate SACK**--->告诉发送方哪些数据是**重复接收**的.

server重复收到数据包的时候,也会恢复SACK数据包.













###### 流量控制（flow-control service）

​	注意，这里解决的是**接收方的应用程序从自己的buffer中取数据的速度跟不上发送方发送数据的速度**。

![image-20250417160829685](../mio/static/img/image-20250417160829685.png)

​	**LastByteRcvd – LastByteRead <=  RcvBuffer**

​	第一个是**接收的序号**，第二个是应用程序**读取的序号**，那么相减就是还有多少内容在**buffer**中。

​	**rwnd = RcvBuffer – [LastByteRcvd – LastByteRead]**

​	那么**rwnd**就是**receive window**的大小，表示我有多少**空闲位置**，注意到上面的**TCP**报文段结构中就有一个Receive window，那么就可以在ack的时候 **捎带（piggy backing）** 这个数据。

> ​	就是返回**ACK**确认的时候,捎带这个**window**的大小,这样发送端就可以根据这个大小来调整发送窗口.

​	当OS比较繁忙的时候,可能会减少接收的缓冲区,但是接收方收缩了缓冲区,发送方收缩了窗口,就有可能导致丢包,所以二者不能同时进行.

###### 窗口关闭(当接收方的窗口返回为0的时候)

> 那么就会停止进行传输.

​	当接收方返回ACK中win = 0的时候,此时发送方会停止发送,但是会开启一个**窗口探测计数器**,定期的向对方进行探测此时窗口的容量.

如果还是0,就会重新启动,如果不是,就会继续当前的传输.

###### *这里还会引发一个问题:Silly Window Syndrome

​	就是接收端很忙,每次的能空出来的窗口小的夸张,但是发送端看到了这几个字节是空的,还急着往对方发送,跟**舔狗**一样,很**愚蠢**!

> 解决方案:
>
> 1.接收方不向对方通告小窗口.
>
> ​	当自己的窗口大小小于MSS以及二分之一缓存的最小值的时候,就向对方通告自己的ACK = 0,停止发送.
>
> 2.发送方不发送小数据.
>
> ​	**Nagle**算法,只有当自己的可用窗口以及可发送数据大于一个MSS,并且收到对方上一次的ACK确认的时候,才会发送数据.(但是比如ssh就要关闭Nagle算法,因为数据之间的交互是比较小的数据.)

###### 两次握手的问题：

​	1.server可能会维护很多**虚假的半连接**。 

​	比如，第一个发送的ack超时，发送了第二个ack，但是第一个又建立了连接之后断开，此时第二个ack就会单方面和server连接。

​	当客户端发送了第一个SYN之后,Server会维护一个SYN(半连接队列)队列,但是此时如果client的ack超时,或者干脆断连,就会导致一个虚假的半连接.

​	2.在断开连接了之后，可能会把旧的才传过来的数据当成新的数据接收。

![image-20250417163939181](../mio/static/img/image-20250417163939181.png)

在 **捎带** 的过程中还确认了对方的**序号空间**。

​	**为什么一定是3次---》 **这里是比较有趣的地方.

> ​	我们在建立连接的过程中也是要确定对方的序号空间,在SYN + SYN/ACK + ACK的过程中确认对方的序号空间.
>
> ```text
> 客户端                            服务端
>   SYN, seq = x   -------------------->
>                     （客户端的初始序号是 x）
>   <--------------------   SYN+ACK, seq = y, ack = x+1
>                     （服务端的初始序号是 y，确认收到 x）
>   ACK, seq = x+1, ack = y+1  -------------------->
>                     （客户端确认收到 y）
> ```

**1.client给server一个初始序号x，2.server返回一个确认，3.server给client一个初始序号，4.client返回一个确认（可以携带数据）。**

> ​	**2.3.两步可以直接合并（捎带），那么一定要三次握手！**
>
> ​	且先不说可靠性,没有三次就无法进行空间的确定.

SYN：就是在**同步序号空间**。 ACK：就是**对于对方的序号空间进行确认**。

3次就解决了上述的两个问题。

**注意,最后一次的从client到server的ACK响应可以携带一部分的数据,也就是"捎带".**

###### 为什么四次挥手?

FIN仅仅代表自己的实体不再发送消息,但是可以接收消息.

Client--->FIN,表示自己不再发送消息,但是可以接收.

Server收到FIN之后,立即返回ACK,表示清楚,但是Server可能还有一些未释放或者未发送的资源,处理完成之后(解除和这个Client的相关的资源之后,才会返回FIN.

> Server端,FIN报文的控制权其实在上层的应用程序,应用程序处理完了之后,才能发送FIN报文--->为什么会分开才能发送.
>
> 但是只要是进程退出了,都一定会给对方发送FIN报文.

###### *一定是4次挥手么? 不是

有两种断开本次TCP连接的函数:

1.**close()**

进程不能从这个socket中读取,也同样不能写入,那么Client在收到了来自于Server的ACK之后的数据包时,会直接返回RST强行断开这次连接.

2.**shutdown()**可以指定我到底是没有发送的能力还是没有接收的能力.

**什么是延迟确认机制?**

​	TCP协议为确保**可靠性**,每次收到一个数据包的时候,都要使用**ACK**进行确认,但是每个都用ACK确认并且直接发送很浪费,我们尽量把这个ACK **捎带(Piggybacking)** 在我们要发送给Client的数据包里,这样显然效率更高,那么要发送ACK时,我们就会等待一会自己有没有要发送的数据包,超过这个时间还没有的话就直接发送过去,或者在这个时间内有两个连续未确认的包,也直接发送,不等待,防止阻塞的出现.

那么**答案**就是:

​	**当没有数据要从Server的应用程序发送,并且打开了延迟确认机制的时候,我们就会把 FIN/ACK 一起确认,这样效率是最高的!这是一种优化,而且大多数情况下都会采取这种优化!**

> ​	这个道理很简单,因为单独发一个**ACK**不划算,所以我们的**ACK**就会等一下,等到应用程序调用**close()**之后,二者绑定发送给**client**更好.

### 3.6 拥塞控制(Congesstion Control)

> 这里解决的是网络中的延迟的问题（解决排队时延），不是上面所提到的关于流量控制的问题。
>
> 就是说不是发和收**谁快谁慢**的问题,而是**网络中太阻塞**造成的问题.

问题：会传很多重复的segment（因为时间过长会重传，但是没有丢包）。

我们会引入cwnd--->就是所谓的拥塞窗口.

如果过了好几跳被丢，那么这个segment的上游传输能力就都被浪费了。

怎么让端系统理解网络中发生的情况。

ATM网络：直接获取网络中的信息来调整（轻微拥塞，拥塞，以及经过路由的最小带宽），就是利用回路反馈的方法，源端先发送，目标端到了之后会再次返回来。

传递的单位叫信元 53B 其中5B是首部 剩下的48是包含数据的部分。

### 3.7 *TCP拥塞控制

端到端的拥塞控制，网络不提供辅助信息。（端系统自己感知）

**cwnd**（拥塞窗口） 我们把速率设置为 **cwnd / RTT** 的大小。

同时我还要满足流量控制要求：

​	**sendWin = min{congWin, revWin}**

概述：两个事件决定我们的具体的算法。

​	1.对于未确认的segment的ack的到达，会让TCP认为没有阻塞，我们就可以增大cwnd。

​	2.对于冗余ack，我们会认为有阻塞，减小cwnd。

##### TCP拥塞算法

> 不断试探丢包的底线......

**慢启动（slow start）**	**快速恢复（fast recovery）**	**拥塞避免（Congestion avoidance）**

​	开始时 cwnd 设置为1,此时速率就是说MSS/RTT，很慢，我们想迅速试探到阈值，那么每当成功接收到一个ack，那么cwnd * 2,也就是指数增长。

> 这里实际上是,每次接收到一个ACK,我们的cwnd就会 + 1.
>
> 那么这样的增加下去,就是**指数性**的增长.

![image-20250419203828292](../mio/static/img/image-20250419203828292.png)

​	**何时结束？**

​	1.当有超时丢包的时候，cwnd = 1,并且记录 ssthresh 为发生拥塞时设置的拥塞窗口大小的二分之一（事情严重）。

> **ssthresh** ---> slow start threshold:临界值

​	2.当达到**ssthresh**时，更换为拥塞避免模式 一个一个增加cwnd。

> ​	实际上是,每来一个ACK,我们会增加 1/cwnd 的大小.--->这就是意味着一次发送,如果全部正确抵达对方,**就会给自己的拥塞窗口** + 1.

> ​	下面就是**快速重传**算法.	

​	3.当收到3个冗余ack(前面那个包你还没给我发!)的时候（事情不严重），直接变成此时的一半 + 3(因为之前那个包没发过去,我们认为此时网络中发生了阻塞)而不是从1开始增加，然后更换为拥塞避免模式并且一个一个增加cwnd。

> ​	在快速恢复的情况下,如果收到了新的**ACK**,就说明原来的问题已经被解决了,直接恢复**cwnd**为**ssthresh**的状态即可.
>

下图就是三种模式相互转换的一个FSM。

#### 为什么一定是3次握手?

1.**防止历史的重复的连接**:就是之前提到的半连接问题.

​	比如一个client发送SYN 90 给server,接着宕机,然后重新发送一个SYN 100,但是之前的server收到了SYN 90,依然给这个client返回 SYN133(server初始化的序列号) + ACK91,但是此时client期望的是ACK101而不是90,这样的话,client会返回RST直接彻底断开二者的连接,而不会使得Server维护一些半连接.

> ​	还有一种情况,就是连续收到一个Client的两次请求,比如SYN90,结果又发了一个SYN100,那么Sever会返回一个Challenge Ack,也就是91,客户端收到之后会返回RST终止这个连接.
>
> ​	两次握手并非无法结束这个半连接,但是会浪费一次传输的机会,三次握手的中间状态决定了,在正式的连接之前就可以终止.

2.确认同步序列号

​	中间一次可以发送并且进行确认,四次优化成三次.

#### 序列号的作用?

> 一是实现了我们上面提到的一些窗口的协议.

​	client和server二者的初始化序列号不一样,这样历史的报文才大概率不会被接收(当然是一个**相同的四元组**的情况,因为**序列空间还会绕回去**,再次**利用时间戳进行判断**),防止出现数据的混乱.

**ISN随机生成算法**:对于一个四元组进行hash,并且加上当前的一个计时器.

#### IP分片为什么TCP还要MSS(最大报文段长度)?

​	很简单,因为**超时重传的机制**,比如一个TCP大包15000byte,如果不在TCP分片,那就只有一个序列号,在IP层分片,IP这些包但凡有一个丢了,所有这15000字节都要重传,很**愚蠢**.所以在TCP分好,IP也不用分(1460byte之内即可),然后按照正常的超时重传机制运行即可.

#### 握手丢失问题

1.第一次握手失败,触发超时重传的机制,重传几次?要多长时间?

```sh
❯ cat /proc/sys/net/ipv4/tcp_syn_retries
6
```

查看系统,最多重传6次,每次重传时间是上一次的2倍.

如果第一次是1s,那么之后就会不断加倍,那么最多就是127s断开连接.

2.第二次握手失败.

​	也就是Server收到了第一次的SYN请求,此时Client收不到来自Server的SYN/ACK,会一直重传上面的SYN,Server已经发了SYN/ACK,但是一直收不到来自Client的ACK,会一直重传SYN/ACK,最多重传几次?

```sh
❯ cat tcp_synack_retries
5
```

最多重传5次.

> 总之,两方都会根据自己的**内核参数**进行重传的操作.

3.第三次握手失败

​	也就是Client发送的ACK传输失败了,显然这个ACK不会重传,而是Server如果没有收到来自客户端的ACK的时候,就会不断重传SYN/ACK,每当Client收到一个SYN/ACK,都会发送一个ACK给Server,这就是基本的机制.

#### SYN攻击

> TCP的执行流程,半连接队列和全连接队列.

![image-20251022170514132](../mio/static/img/image-20251022170514132.png)

生成很多不同的IP地址发送SYN到Server,把半连接队列充满,这样就接受不到新的真正需要服务的连接了.

解决办法:

1.**backlog**,当网卡接收的速度大于内核处理的速度时,用一个队列暂时存放.

2.扩大**SYN**队列.

3.当SYN队列充满的时候,启用**syn_cookies**:

```sh
❯ cat /proc/sys/net/ipv4/tcp_syncookies
1
```

​	接到一个**SYN**包的时候,计算一个**cookie**返回给Client,相当于不用保存这个状态,之后受到ACK的时候,再去检查是否合法即可.

4.直接减少重传次数即可.

> 可以看到并没有什么很天才的方法直接判断一个SYN,或者大概率判断一个SYN是否是恶意的.

#### 挥手丢失的问题

第一次挥手丢失

client类似于前面的机制,进行超时重传FIN,如果每次重传都失败,那就等待一段时间,接着close();

第二次挥手丢失

如果来自server的ACK丢失,还是类似,client会不断重传FIN,并且和上面一样.

第三次挥手丢失

​	server收到来自于client的FIN请求之后,会自动回复ACK,并且进入**CLOSE_WAIT**状态,这是在等待使用这个TCP连接的应用程序close().

​	如果此时,应用程序调用了close(),server会发送FIN给client,并且进入LAST_ACK状态,如果没有收到ACK,就和上面一样进行超时重传.

第四次挥手丢失

​	当client收到了FIN报文之后,立即返回ACK,并且开启一个时长为**2MSL(Maximum Segment Lifetime，最大报文段生存时间)**的定时器,这意味着这个时间内,是足够server收到ACK的,如果没有收到,自己也来得及接收重传的FIN报文(因为server没有收到ACK的时候就会不断重传FIN),而每一次接收到server重传的FIN报文,就重置这个定时器,定时器结束之后,直接断开连接.

##### 为什么这里要等待2MSL?

可以允许丢包一次,Linux默认的MSL为30s.

#### *具体探讨一下TIME_WAIT状态

##### 为什么要这个状态?

​	1.这也是为什么**2MSL**的一个原因,**server**和**client**可能建立多次的连接,如果上一次TIME_WAIT时间过短,那么旧的数据包可能会在产生一次新连接之后再次作用,我们就等待2MSL的时长,这样可以保证这个时长之内,上一次连接的所有数据包都会失效.

> **"因为是我主动发起关闭的,而你是被关闭的一方,所以在最后的最后,我有义务保证你优雅的关闭......"**

​	2.等待的时间,也是为了保证,**被关闭的一方可以正常的关闭**,和上面提到的第四次挥手失效的原理是一样的.

但是一段时间内维护的**TIME_WAIT**太多,会占用很多系统和端口上的资源,并不好.

**server**一般也不会主动断开连接,**TIME_WAIT**都应该让客户端去承受.

##### 什么时候Server会出现很多TIME_WAIT?

​	1.禁用**http Keep Alive**的时候,一般都是由**server**关闭连接(client发送http请求中携带Connection:close,那么server作出http响应之后,就应该直接关闭连接),并且只要两方有任意一边没有开启http keep alive的话,都会由server主动关闭连接.

​	2.现在我们正常使用**http keep alive**,也就是长连接,建立在一个TCP连接之上,我们不断进行http请求和响应,但是显然要设置一个**定时器**(不可能一直处于连接的状态,比如**nginx**就会配置这个时间),如果客户端在这期间没有请求的话,server就会进入TIME_WAIT的状态.

比如

```json
http {
    include       mime.types;
    default_type  application/json;

    sendfile        on;
    
    keepalive_timeout  65;

    server {
        listen       8080;
        server_name  localhost;
        # 指定前端项目所在的位置
        location / {
            root   html/hmdp;
            index  index.html index.htm;
        }

        error_page   500 502 503 504  /50x.html;
        location = /50x.html {
            root   html;
        }


        location /api {  
            default_type  application/json;
            #internal;  
            keepalive_timeout   30s;  
            keepalive_requests  1000;  
            #支持keep-alive  
            proxy_http_version 1.1;  
            rewrite /api(/.*) $1 break;  
            proxy_pass_request_headers on;
            #more_clear_input_headers Accept-Encoding;  
            proxy_next_upstream error timeout;  
            proxy_pass http://127.0.0.1:8081;
            #proxy_pass http://backend;
        }
    }

    upstream backend {
        server 127.0.0.1:8081 max_fails=5 fail_timeout=10s weight=1;
        server 127.0.0.1:8082 max_fails=5 fail_timeout=10s weight=1;
    }  
}
```

这里超时时间就是**65s**.

同时这里还有:

```conf
keepalive_requests  1000;  
```

这意味这一条TCP连接(http长连接)最多处理多少次请求,大于这个请求的时候,server就会自动关闭连接.

如果**server**的进程崩溃,内核会代替它和**client**进行剩下部分的通信.
